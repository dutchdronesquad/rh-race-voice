# Race-audio latency correlation telemetry

Race-day capture for #487 builds on the correlation telemetry from #304, part of epic #296. Hardware and audible validation remain outstanding; queue acceptance does not establish gate-to-speaker latency.

## What's implemented

`sendspin_service/race/telemetry.py` adds one dependency-free function, `record(event_id, stage, **fields)`, that logs a single-line JSON object (`event_id`, `stage`, a monotonic `t`, plus whatever fields the call site passes) through the `sendspin_service.telemetry` logger. It does nothing when INFO logging is not enabled for that logger, so it stays cheap on an idle service.

The `received` record includes event kind, pilot ID, lap number, heat ID and generation for HTTP events. Intermediate records cover admission, synthesis timing, cache hits, prefix publication and output scheduling. Final records are owned by preparation until audio is published, then by each configured output independently.

Before fan-out, a rejected, expired, cancelled or failed preparation produces one `output_dropped` without a destination. That global outcome covers the outputs that never received audio. After fan-out, each configured destination produces exactly one of `output_played`, `output_dropped` or `output_filtered`. Filtering has `reason=selection`; a broken filter has `reason=filter_failed`. A service with no outputs reports `no_destinations`. Output-local receipt state prevents a late sink reply, an interrupt and shutdown from reporting multiple final outcomes for the same admitted output. It is retained only with the bounded output item, not in a growing global event registry.

`output_played` is the existing stage name and now carries `delivery=queued`: the sink or relay accepted the audio. It does not confirm that a speaker produced sound. An output already marked queued can later have its buffered audio cleared; its original queue outcome is not rewritten. Preparation that published an early prefix leaves final accounting to the outputs, including when its time generation is cancelled or fails. A prefix reserves output order and lets the relay populate its content cache during synthesis; local playback waits for complete audio. `prefix_ready` is not evidence that any segment has been played.

Pending expiry, invalidation, preemption, playback failure, stop-barrier failure and shutdown are explicitly recorded. Reasons include `expired`, `superseded`, `preempted`, `state_changed`, `heat_changed`, `competition_changed`, `voice_changed`, `session_changed`, `cache_clear`, `shutdown`, `synthesis_failed`, `synthesis_empty`, `synthesis_incomplete`, `playback_failed`, `stop_failed`, queue-capacity reasons and `sink`/`relay_error` when delivery did not succeed. `state_changed` covers a generation change whose wire snapshot does not distinguish an operator stop from a new staging sequence.

`tests/test_outcome_lifecycle.py` exercises pending and active cancellation, expiry pruning, shutdown, independent outputs and late replies. Existing HTTP burst and progressive-speech scenarios additionally verify that accepted work is accounted for under preparation or playback overload. These tests validate event handling and queue outcomes, not physical audio playback.

`tests/test_race_session.py` runs two complete six-round races, with four and eight pilots, through real HTTP admission, the production planners, speech planning, RAM reuse and a real synthesis-worker pipe. Only native voice generation and speaker output are replaced by controlled fakes. The scenarios start cold, explicitly prepare audio, then exercise warm prefixes, repeated bursts, explained overflow, a duplicate event, the finish buzzer and winner, heat changes, stop, expiry, a worker subprocess crash and recovery, a fresh staging signal and shutdown with work outstanding. A full output and an even-pilot selection are audited independently. Every accepted event must have exactly one global preparation failure or one final record per configured output; completed lap deliveries must contain all three segments without duplicate clips and preserve passage order. The RH adapter integration separately sends a `lap=None` finish payload before a winner and verifies that the invalid lap triggers no synthesis while the winner still reaches the service.

## Capturing a baseline

The service automatically records race-audio diagnostics for as long as it runs, on both primary and relay instances. Put the timer in the field and race normally; there is nothing to enable before a race or to stop afterwards. After an issue, or after the evening, request an export:

```sh
sendspin-service diagnostics export
```

The ZIP is saved in the current directory as `race-audio-YYYY-MM-DD-HHMMSSZ.zip`, using UTC. Use `--output race-audio-primary.zip` to choose another path or name. Existing files are never overwritten. Export leaves recording running. `sendspin-service diagnostics status` reports recording health. The CLI reads the local API URL and `SENDSPIN_API_TOKEN` from `/etc/default/sendspin-service`, with an environment token taking precedence. Use `--env-file PATH` for another configuration or `--url https://audio.example.com` to export from a remote relay. The read-only `/v2/diagnostics/status` and `/export` endpoints use the existing service API authentication; listener controls do not grant export access.

Records are persisted on disk and kept when the service restarts. The default directory is `diagnostics` beside the race-cache directory, under the service state directory for packaged installations. Override it with `SENDSPIN_DIAGNOSTICS_DIR` or `serve --diagnostics-dir PATH`. The manifest keeps context for the current capture and up to 20 previous captures so restarts remain distinguishable.

The service retains eight rotating files of up to 8 MiB each (64 MiB total), with a bounded queue of 2,048 records. This provides space for multiple races throughout an evening, rather than a short debugging window. Retention is size-based: sufficiently heavy or prolonged use eventually replaces the oldest records. Export after the evening if you want to keep it longer. Only diagnostic events are written; idle time does not generate periodic disk writes. Telemetry stays out of the ordinary service journal, avoiding a second unbounded copy.

Disk writes and ZIP construction run off the audio event loops. A full queue drops diagnostic records instead of delaying audio; storage failures disable writes and appear in status/export without preventing service startup. Recording excludes speech text, audio, pilot names, service URLs and tokens. Numeric race IDs and model names remain available for correlation.

The ZIP includes a versioned `manifest.json` with capture and clock IDs, service/dependency versions, architecture, available device model and output configuration; retained JSONL events; `summary.json`; and interpretation notes. Summaries group each service clock and destination separately, report drop reasons and timing distributions with sample counts, and show p95 only with at least 20 samples and p99 with at least 100. Counts cover retained records only; rotation or recorded loss can leave an event without all its stages.

Worker queue wait is distinct from synthesis request time. Segment index/cache location, disk/RAM cache hits, preparation time, output waits, relay upload/delivery attempts, Sendspin planned starts, tone lateness, timestamp gaps and scheduling lead help locate a delay. Some waits overlap; do not add all durations together. A gap between deliberately separate tones is different from a timestamp gap inside one WAV. `output_played` still means queued, not audible.

The browser player also automatically keeps recent measurements while the page is open. In **Diagnostics**, use **Download recording** after an issue; **Mark audio issue** is an optional marker when you hear one. The separate JSON retains the latest 1,200 half-second samples (about ten minutes in an active tab) and 200 connection/marker events. Background-tab throttling can reduce sampling. It records available buffer runway, resync counters, time-sync uncertainty, output latency and render timestamps; unsupported measurements are `null`. Browser recordings stay in the tab until downloaded and are lost on reload. Download them alongside the corresponding primary and relay ZIPs.

Service `t` values are monotonic and comparable only within the same `clock_id`; shared `event_id` values link primary and relay stages without subtracting their clocks. Browser `performance.now()` is another clock domain. Its server timestamp is the SDK's mapped estimate with reported sync uncertainty, not a shared raw clock. A zero buffer or resync is an observation, not proof of a speaker underrun. WindowsSpin connection/product information is available from the service, but authoritative Windows render, underrun and speaker timing are unavailable through this integration. Record its version and observations separately.

## What remains outstanding

Remaining validation includes sustained hardware runs, audible output, Raspberry Pi capacity, player synchronization and buffering, numerical latency acceptance gates and mode-by-mode comparisons. Deterministic regressions do not establish gate-to-speaker latency or hardware acceptance. Worker, player and network failures still need broader combined coverage beyond the existing focused tests. No benchmark or production-service changes are needed to run the regression suite.
